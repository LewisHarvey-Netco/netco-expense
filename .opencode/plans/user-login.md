# User Login Feature

## 1. Goal

Add authentication to Netco Expense: users must log in with email +
password to access the site. Two roles exist — **consultant** (logs
expenses) and **finance** (reviews, approves, or flags expenses that
break the rules). Since there's no backend yet, users are hardcoded in a
mock JSON file, with a tracked TODO to replace this with real backend
auth later. Login also introduces the app's first real UI system:
Tailwind v4 + shadcn/ui (replacing the current hand-rolled CSS), React
Router v7 for navigation/route-guarding, and Vitest for automated tests.

## 2. Current State

- Fresh Vite 8 + React 19 + TS 6 scaffold. `src/App.tsx` renders a static
  "Hello world" `<div>`. No router, no state management, no component
  folders — everything is flat in `src/` (`main.tsx`, `App.tsx`,
  `App.css`, `index.css`).
- `src/index.css` has a hand-rolled design system: CSS custom properties
  (`--text`, `--bg`, `--accent` = `#aa3bff`, etc.), light/dark mode via
  `prefers-color-scheme`, and global element styles (`#root`, `h1`,
  `h2`, `code`). This will be fully replaced.
- `package.json` deps: only `react` + `react-dom` at runtime;
  `@vitejs/plugin-react`, `oxlint`, `typescript`, `vite` as dev deps. No
  router, no form library, no test runner, no Tailwind/shadcn.
- `tsconfig.app.json` has no `@/*` path alias. `vite.config.ts` has no
  `resolve.alias`. Both need one for shadcn's CLI to work.
- `AGENTS.md` "Stack" section lists only Vite/React/TS/npm/oxlint — needs
  updating once new conventions land.
- No `TODO.md` exists yet at repo root (separate from `problems.md`,
  which is reserved for agent-workflow friction, not app follow-ups).

## 3. Key Decisions (from interview)

- **Scope:** Login only. No sign-up UI (mock data simulates "already
  signed up" users, each with a `role` as if chosen at signup).
- **Mock users:** `src/mocks/users.json`, 2 users — 1 consultant, 1
  finance — sharing a simple password (`password123`) for easy testing.
  Plaintext passwords (acceptable for a mock-only demo, flagged as such).
- **Auth state:** React Context (`AuthContext`), persisted to
  `sessionStorage` (survives refresh, clears on tab/browser close).
- **Routing:** `react-router-dom` v7, classic JSX API
  (`<BrowserRouter>`/`<Routes>`/`<Route>`, not the data-router/loader
  API).
  - `/login` — login form.
  - `/expenses` — consultant home (placeholder page).
  - `/review` — finance home (placeholder page).
  - `/` — always redirects: to role home if logged in, `/login` if not.
    No content of its own.
  - `*` (catch-all) — redirects to `/`. No dedicated 404 page.
- **Route guarding:** `<ProtectedRoute allowedRoles={...}>` wrapper.
  Unauthenticated → redirect to `/login`. Authenticated but wrong role
  (e.g. consultant hitting `/review`) → redirect to their own role home.
  No "remember where I was going" — always land on role default home
  after login, regardless of what URL was originally attempted.
- **Logout:** Button in a shared `Header` component (visible on
  `/expenses` and `/review`), clears context + `sessionStorage`, redirects
  to `/login`.
- **Login form validation:** Client-side email regex format check first;
  then match against mock users (case-insensitive email, exact password).
  On any failure, show one generic error: "Invalid email or password"
  (doesn't reveal which field was wrong).
- **Form stack:** `react-hook-form` + `zod` + shadcn's `Form` component.
- **Styling:** Tailwind v4 (CSS-first `@theme`, `@tailwindcss/vite`
  plugin, no `tailwind.config.js`) + shadcn/ui (New York style,
  `lucide-react` icons, "neutral" base color). `src/index.css` is fully
  replaced by Tailwind + shadcn's generated CSS variables. Netcompany
  brand colors override shadcn's theme tokens:
  - `--primary` → `#0F1F47` (dark navy)
  - `--secondary` → `#123836` (dark teal)
  - `--accent` → `#E4601F` (orange)
  - Everything else (background, foreground, border, muted, destructive)
    stays shadcn's default neutral values.
  - Light mode only — no dark mode this pass.
- **shadcn components to install:** `button`, `input`, `label`, `form`,
  `card`, `alert`, `badge`.
- **Header/nav:** App name "Netco Expense" on the left; on the right,
  user's name + role `Badge` (e.g. "Alice · Consultant") + plain Logout
  `Button`. No dropdown/avatar.
- **Placeholder pages:** `/expenses` and `/review` are each a `Card` with
  a heading and one line of placeholder text (no fake data tables).
- **Folder structure:**
  ```
  src/
    mocks/
      users.json
    context/
      AuthContext.tsx
    components/
      ProtectedRoute.tsx
      Header.tsx
      ui/                 (shadcn-generated components)
    pages/
      LoginPage.tsx
      LoginPage.test.tsx
      ExpensesPage.tsx
      ReviewPage.tsx
    lib/
      utils.ts            (shadcn's cn() helper, auto-generated by init)
    types.ts               (shared User/Role types)
    App.tsx                (router setup)
    App.test.tsx           (integration test: login -> redirect flows)
  ```
- **Testing:** Vitest + React Testing Library, colocated test files.
  - `src/App.test.tsx` — one file, integration-style, covering:
    1. Login as finance → lands on `/review`.
    2. Login as consultant → lands on `/expenses`.
    3. Visiting `/` while logged in (each role) → redirects to correct
       role page.
    4. Failed login (bad credentials) → shows "Invalid email or
       password" validation error.
- **TODO.md:** New file at repo root, containing only the item to remove
  mocked users / replace with real backend auth once one exists.
- **AGENTS.md:** Updated to document new stack (React Router v7, Tailwind
  v4, shadcn/ui, react-hook-form + zod, Vitest + RTL) and the
  `pages/components/context/mocks/lib` folder convention.

## 4. Proposed Changes

### 4.1 Dependencies

Install runtime deps:
- `react-router-dom` (v7)
- `react-hook-form`, `zod`, `@hookform/resolvers`
- `tailwindcss` (v4), `@tailwindcss/vite`
- shadcn/ui runtime deps as pulled in by its CLI (`class-variance-authority`,
  `clsx`, `tailwind-merge`, `lucide-react`, plus Radix primitives for each
  installed component — CLI manages this automatically per component)

Install dev deps:
- `vitest`, `@testing-library/react`, `@testing-library/jest-dom`,
  `@testing-library/user-event`, `jsdom`

Add npm script: `"test": "vitest run"` in `package.json`.

### 4.2 Path alias setup (required before shadcn init)

- `tsconfig.app.json`: add `"baseUrl": "."` and
  `"paths": { "@/*": ["./src/*"] }` under `compilerOptions`.
- `vite.config.ts`: add `resolve: { alias: { '@': path.resolve(__dirname,
  './src') } }` (import `path` and `fileURLToPath`/`node:url` as needed
  for ESM `__dirname` equivalent).

### 4.3 Tailwind v4 + shadcn/ui init

- Run `npx tailwindcss init` equivalent via `@tailwindcss/vite` plugin
  registration in `vite.config.ts` (`plugins: [react(), tailwindcss()]`).
- Replace `src/index.css` entirely with Tailwind's `@import "tailwindcss"`
  plus shadcn's generated `@theme`/CSS variable block (via
  `npx shadcn@latest init`, selecting: New York style, lucide-react icons,
  neutral base color, CSS variables mode, Vite framework detection).
- After shadcn init generates its default neutral theme tokens, override:
  - `--primary` (and `--primary-foreground` for contrast) → navy
    `#0F1F47` with a light foreground.
  - `--secondary` (and `--secondary-foreground`) → teal `#123836`.
  - `--accent` (and `--accent-foreground`) → orange `#E4601F`.
  - Leave `--background`, `--foreground`, `--border`, `--muted`,
    `--destructive`, etc. as shadcn's generated neutral defaults.
- Delete `src/App.css` (Tailwind utility classes replace its role; it's
  currently just an empty file).
- Install shadcn components: `npx shadcn@latest add button input label
  form card alert badge` → generates `src/components/ui/*.tsx` and
  `src/lib/utils.ts`.

### 4.4 Types and mock data

- `src/types.ts`: define `type Role = 'consultant' | 'finance'` and
  `interface User { id: string; name: string; email: string; role: Role
  }` (password intentionally excluded from this shared type — it's only
  read from the raw mock JSON during login, never carried in app state).
- `src/mocks/users.json`: array of 2 objects —
  ```json
  [
    { "id": "u1", "name": "Alice Nielsen", "email": "alice@netcompany.com", "password": "password123", "role": "consultant" },
    { "id": "u2", "name": "Bob Madsen", "email": "bob@netcompany.com", "password": "password123", "role": "finance" }
  ]
  ```
  Add a `// NOTE:` — since this is JSON, use a leading comment in the
  consuming TS file instead (JSON doesn't support comments) — see
  `AuthContext.tsx` below.

### 4.5 Auth context

- `src/context/AuthContext.tsx`:
  - Import `usersData` from `../mocks/users.json` with a top-of-file
    comment: `// MOCK DATA: hardcoded users for frontend-only demo. See
    TODO.md — replace with real backend auth.`
  - `AuthContext` provides: `{ user: User | null; login: (email: string,
    password: string) => { success: boolean; error?: string }; logout: ()
    => void }`.
  - On mount, hydrate `user` from `sessionStorage` (key e.g.
    `netco-expense-auth`) if present.
  - `login()`: validates email format via regex
    (`/^[^\s@]+@[^\s@]+\.[^\s@]+$/`) first — if invalid, return `{
    success: false, error: 'Invalid email or password' }` (same generic
    message, don't leak format-vs-mismatch distinction per the
    "don't reveal which field was wrong" decision... actually re-check:
    format validation happens in the form/zod layer before calling
    login(), so login() itself only handles credential matching against
    mock users — see 4.6). Matches case-insensitive email + exact
    password against `usersData`; on match, sets `user` (without
    password field), writes to `sessionStorage`; on no match, returns
    `{ success: false, error: 'Invalid email or password' }`.
  - `logout()`: clears `user` state and removes the `sessionStorage` key.
  - Export a `useAuth()` hook wrapping `useContext(AuthContext)`.

### 4.6 Login form (zod + react-hook-form + shadcn Form)

- `src/pages/LoginPage.tsx`:
  - zod schema: `email: z.string().email('Invalid email or
    password')` (reuses the generic message so the field-level error
    matches the design decision) and `password: z.string().min(1,
    'Invalid email or password')`.
  - On valid submit, call `auth.login(email, password)`. If it returns
    `success: false`, show the generic error (e.g. via shadcn `Alert`
    component above the form, or a `FormMessage`-style banner — use
    `Alert` with `variant="destructive"`).
  - On success, `navigate` to the user's role home (`/expenses` or
    `/review`) using `react-router-dom`'s `useNavigate`.
  - Layout: centered shadcn `Card` with `CardHeader` (title "Netco
    Expense" or "Sign in"), `CardContent` containing the `Form` with
    `email`/`password` `Input` fields (via shadcn `FormField`) and a
    submit `Button`.

### 4.7 Routing, guards, header, placeholder pages

- `src/components/ProtectedRoute.tsx`: takes `children` and optional
  `allowedRoles?: Role[]`. Reads `useAuth()`. If no `user`, `<Navigate
  to="/login" replace />`. If `allowedRoles` is set and `user.role` isn't
  included, `<Navigate to={roleHome(user.role)} replace />`. Otherwise
  render `children`.
- Add a small helper `roleHome(role: Role): string` (e.g. in
  `src/types.ts` or a new `src/lib/roleHome.ts`) mapping
  `consultant` → `/expenses`, `finance` → `/review`. Reused by
  `ProtectedRoute`, the `/` redirect, and post-login navigation.
- `src/components/Header.tsx`: shows "Netco Expense" title, plus (when
  `user` present) `{user.name}` + role `Badge` + Logout `Button` calling
  `auth.logout()` then navigating to `/login`.
- `src/pages/ExpensesPage.tsx` / `src/pages/ReviewPage.tsx`: each wraps
  `Header` + a `Card` with a heading ("Expenses" / "Review Queue") and
  placeholder text ("Expense submission form coming soon." / "Expense
  review queue coming soon.").
- `src/App.tsx`: wrap everything in `<AuthProvider>` and
  `<BrowserRouter>`. Routes:
  ```
  <Route path="/login" element={<LoginPage />} />
  <Route path="/expenses" element={<ProtectedRoute allowedRoles={['consultant']}><ExpensesPage /></ProtectedRoute>} />
  <Route path="/review" element={<ProtectedRoute allowedRoles={['finance']}><ReviewPage /></ProtectedRoute>} />
  <Route path="/" element={<RootRedirect />} />
  <Route path="*" element={<Navigate to="/" replace />} />
  ```
  `RootRedirect` is a small inline component: if `user`, `<Navigate
  to={roleHome(user.role)} replace />`; else `<Navigate to="/login"
  replace />`.

### 4.8 Testing setup

- `vite.config.ts` (or a separate `vitest.config.ts` merged via
  `mergeConfig`): add `test: { environment: 'jsdom', setupFiles:
  ['./src/setupTests.ts'], globals: true }`.
- `src/setupTests.ts`: `import '@testing-library/jest-dom'`.
- `src/App.test.tsx`: renders `<App />` (with its own internal
  `BrowserRouter`, or wrap in `MemoryRouter` if easier to control
  initial route — prefer rendering `<App />` as-is and using
  `window.history`/`initialEntries` pattern via a testable router setup;
  if `App.tsx` hardcodes `<BrowserRouter>`, that's fine for jsdom, tests
  navigate by simulating clicks and asserting `location.pathname` via
  `window.location` or by checking rendered page content, e.g. "Review
  Queue" text appears). Four test cases per section 3 above:
  1. Fill login form as `bob@netcompany.com` / `password123` (finance)
     → assert `/review` content ("Review Queue") renders.
  2. Fill login form as `alice@netcompany.com` / `password123`
     (consultant) → assert `/expenses` content ("Expenses") renders.
  3. For each role, log in, then confirm visiting `/` (e.g. via
     `history.pushState` + rerender, or by checking the redirect already
     landed correctly post-login since login itself navigates to role
     home — treat this as: after login, manually trigger navigation to
     `/` and assert it bounces back to the correct role page).
  4. Submit with a bad password (e.g. correct email, wrong password) →
     assert "Invalid email or password" text is shown, no navigation
     occurs.
- Clear `sessionStorage` in a `beforeEach`/`afterEach` to isolate tests.

## 5. Verification

Run in order, fixing issues before proceeding:
1. `npm run build` — TypeScript project check + Vite production build
   must succeed with no type errors.
2. `npm run lint` — oxlint must pass.
3. `npm run test` — all Vitest cases in `App.test.tsx` must pass.
4. Manual smoke test via `npm run dev`:
   - Load `/` while logged out → redirected to `/login`.
   - Try an invalid email format (e.g. `notanemail`) → inline validation
     error, no request "sent".
   - Try wrong credentials → generic "Invalid email or password" alert.
   - Log in as `alice@netcompany.com` / `password123` → lands on
     `/expenses`, header shows "Alice Nielsen" + "Consultant" badge.
   - Manually navigate to `/review` while logged in as Alice → bounced
     back to `/expenses`.
   - Click Logout → redirected to `/login`, `sessionStorage` cleared.
   - Log in as `bob@netcompany.com` / `password123` → lands on
     `/review`, header shows "Bob Madsen" + "Finance" badge.
   - Manually navigate to `/expenses` while logged in as Bob → bounced
     back to `/review`.
   - Refresh the page while logged in → still logged in (session
     persists via `sessionStorage`).
   - Visit an unknown path (e.g. `/foo`) → ends up redirected to role
     home or `/login`.

## 6. Risks / Open Questions

- **shadcn CLI version drift:** `npx shadcn@latest` will pull whatever is
  current at execution time; exact generated file contents (theme
  variable names, component internals) may differ slightly from what's
  described here. Treat this plan's CSS variable names as intent, not a
  literal diff — adapt to whatever shadcn's init actually scaffolds.
- **Contrast/accessibility of navy/teal/orange overrides:** shadcn
  expects paired `-foreground` tokens for each color for text contrast;
  these need to be chosen manually (e.g. white/near-white text on navy
  primary) since Netcompany's guidance only specifies the three base
  hex codes, not paired foreground colors.
- **Router + jsdom test interaction:** simulating full navigation
  (including the `/` redirect check) in RTL/jsdom can be fiddly
  depending on whether `App.tsx` owns its own `<BrowserRouter>`. The
  implementer may need to adjust test setup (e.g. extracting routes into
  a testable component separate from the `<BrowserRouter>` wrapper) to
  control the initial URL per test case.
- **Plaintext passwords in mock JSON:** acceptable only because this is
  a frontend-only demo with a tracked TODO to remove it; flagged here so
  it isn't mistaken for a real security decision.
- **No sign-up flow:** deferred entirely; future sessions building
  sign-up will need to decide how new users' roles get chosen/stored,
  which is out of scope here.
